# Niral Public Project Growth Checklist

Use this with the Visual Form Builder project. It is a recommended engineering workflow, not an official GHFind checklist or a promise of points. Keep real response data private even when the application source is public.

## Phase 0 Scope attribution and baseline

- [ ] Record the actual implementation folder and verified public repository URL under the intended Niral account.
- [ ] Preserve actual author identity and confirm ownership of published code and assets.
- [ ] Keep private customer material, secrets and real response exports out of the repository.
- [ ] Describe one useful first form journey and its intended users.
- [ ] Capture a fresh GHFind baseline when available; record scan date, scoring release and historical/fresh status.

Score support: public project evidence and accurate attribution. A fresh score is a measurement, not a prerequisite for coding.

## Phase 1 Usable original repository

- [ ] Implement working functionality rather than only a marketing page.
- [ ] Explain the problem and include exact setup commands in the README as they become available.
- [ ] Record runtime requirements, dependency versions and sample configuration with placeholders.
- [ ] Choose an appropriate license and acknowledge third-party assets/code.
- [ ] Provide synthetic forms, answers and a reproducible demonstration.
- [ ] Test installation from a clean checkout before calling the release usable.

Score support: original project substance; genuine recognition may develop later. Cosmetic edits alone do not guarantee points.

## Phase 2 Plan each useful change

- [ ] Select exactly one eligible task ID and confirm its prerequisites.
- [ ] State the actual user problem and the task's individual completion check.
- [ ] Search existing issues before creating an issue when coordination requires one.
- [ ] Keep the change logically complete and avoid artificial task/PR splitting.
- [ ] Record blockers or unrelated findings separately.

Do not create an issue merely to add activity. Individual task checks and whole-release gates have different scopes.

## Phase 3 Build verify and integrate

- [ ] Implement the selected behaviour according to shared schemas and architecture.
- [ ] Preserve version/response consistency, tenant boundaries and relevant failure behaviour.
- [ ] Add or update meaningful tests appropriate to the change.
- [ ] Verify browser behaviour for affected UI where possible.
- [ ] Update changed contracts, examples and documentation.
- [ ] Review the final diff and resolve actual feedback.
- [ ] Preserve actual authorship and record self-review honestly when no independent reviewer is involved.
- [ ] Commit/push only when authorized and verify the correct repository and remote commit.

Score support: contribution quality and authentic engineering activity. Do not claim accepted external work or independent review that did not happen.

## Phase 4 Release a complete workflow

- [ ] Meet the relevant milestone gate rather than marking every future feature done.
- [ ] Run create-publish-submit-inspect-export on the actual running stack.
- [ ] Check closing, invalid input, duplicate retry and historical-version behaviour.
- [ ] Check required accessibility, data-lifetime and deployment evidence.
- [ ] Publish versioned release notes and a synthetic demo when that release task is authorized.
- [ ] Document limitations and the path for reporting reproducible problems.

Releases help adoption and maintenance. Each tag is not a guaranteed score increment.

## Phase 5 Discovery and genuine use

- [ ] Pin the useful repository on the intended profile when appropriate and authorized.
- [ ] Publish a practical tutorial or sample for features that actually work.
- [ ] Invite testers to complete a concrete form workflow when outreach is authorized.
- [ ] Record observed feedback and respond to real issues.
- [ ] Welcome useful contributions and acknowledge contributors.

Score support: genuine community recognition and possible future impact. Never invent downloads, users, followers or adoption. Do not buy stars or trade follows.

## Phase 6 Maintenance and ecosystem work

- [ ] Triage actual failures and prioritize problems affecting users.
- [ ] Maintain dependency compatibility, tests and setup instructions.
- [ ] Release fixes when useful changes are ready.
- [ ] Investigate an upstream issue when it actually blocks the product.
- [ ] Follow the upstream contribution guide and submit a verified fix when appropriate.
- [ ] Extract a reusable renderer/schema package only after a stable need emerges.

Score support: maintained projects and relevant ecosystem work. Forty days of local changes do not guarantee broad ecosystem reach.

## Phase 7 Review progress over time

- [ ] Record useful releases, accepted changes, reproducible examples and actual user outcomes.
- [ ] Compare fresh category scores from compatible scoring releases when available.
- [ ] Distinguish changed rules, stale scans and attribution gaps from code quality.
- [ ] Select the next useful task and continue project maintenance across years.

Account maturity requires time. Completing this checklist does not maximize every category.

## Per run record

Record each phase as Completed for this run, Pending, Not applicable or Blocked, with a short reason and evidence. Evaluate all checkpoints, but avoid copying a long unchanged table after every small change; preserve a baseline matrix and record the checkpoints changed by this run. A phase may contain both completed and pending items. Never mark a whole release or adoption phase permanently complete after one task.

| Category | Main evidence | What a single task cannot guarantee |
|---|---|---|
| Original and led projects | Useful original implementation and attributable maintenance | Popularity |
| Contributions | Useful accepted changes and honest review history | External acceptance |
| Activity | Continued real development and investigation | A meaningful result from an empty streak |
| Ecosystem | Qualifying impact and adoption | Broad reach from a new repository |
| Community | Interested users and followers | Guaranteed audience growth |
| Maturity | Account age and active years | Instant maturity points |

References: [GHFind methodology](https://ghfind.com/en/methodology) and [GitHub account attribution](https://docs.github.com/en/get-started/learning-about-github/types-of-github-accounts).
